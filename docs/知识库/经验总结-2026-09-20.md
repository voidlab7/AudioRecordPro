# 经验总结（Tab，截至 2026-09-20）

> 覆盖 2026-09-17~09-20 三段实战：E2E 首链路跑通、BUG-1 日志取证、V1.2 完成度审查、转写/格式选型。
> 定位：这些是**方法论层面的可复用经验**，不是需求也不是缺陷记录。

## 一、E2E 自动化测试（computer-use）

| # | 经验 | 细节 |
|---|---|---|
| 1 | **不轻信 UI，落盘硬验证** | UI 显示「✅ 导出成功」不算数；`afinfo` 验编码/时长 + Python wave 解析 RMS/峰值验「真实音频非静音」才算数。本轮 RMS 7499/峰值 28279 才敢判 PASS |
| 2 | **NSPopUpButton 下拉菜单的 ax 点击不可靠** | 菜单项点击会静默回弹（选了 WAV 仍是 M4A）。可靠做法：点开菜单 → `get_app_state` **当帧**确认菜单开着 → 用**当帧坐标**点菜单项。键盘（down+return）也不稳 |
| 3 | **导出链路有隐藏第二跳** | 导出卡片点「导出」后还会弹系统 NSSavePanel——用例设计必须把这一跳算进去，否则自动化脚本会卡在「点了一次导出没反应」 |
| 4 | **截图权限分层** | 终端 `screencapture` 无 TCC 屏录权限（报 could not create image），computer-use 插件有；且**后台窗口截图全黑**，先激活到前台再截 |
| 5 | **状态观察要抓「不一致」** | 「●● 录制中」但计时器 00:00 的文案 bug，就是靠切标签页前后对比状态栏发现的——初始态截图留底是值得的 |

## 二、Bug 取证（BUG-1：计时器与录制管线脱节）

- **日志时间线重建是最强武器**：UI 计时器 00:36:47 起走，但管线日志 00:36:47–00:45:14 零记录 → 直接证明 `startMultiSourceRecording` 根本没被调用，UI 状态是 0.3s 定时器假装的。**「日志空洞」本身就是证据**。
- 取证套路：`grep -n 关键事件` 拿行号 → `sed -n` 切时间窗 → 过滤噪声（AudioProcessEnumerator 每 2s 全量刷）→ 时间线闭合才能下结论。
- **副作用发现**：一天 13.5MB 日志——高频枚举日志必须加节流，否则日志本身就是性能负担。
- 修复四方向已挂 TODOS.md：录制态以 recorder 回调为准 / stop 无条件可达 / 0 秒录音拦截 / 编辑器 0 buffer 容错。

## 三、完成度审查（文档 vs 代码）

- **代码是唯一事实源**：REQ-1.2-01/02 文档标「⬜ 待开发」，实测代码已完成 40%/70%。审查完成度永远走「读代码 + 看运行时产物」双验证，文档状态只当线索。
- **验收标准逐条对账**：体积超标 4 倍（80MB vs <20MB）、License 踩 GPL 红线、参数配置零实现——不逐条对账就发现不了「形式上有产物、实质不符」。

## 四、技术选型

| # | 经验 |
|---|---|
| 1 | **先查 Apple 原生，再上三方**：MP3 用 ExtAudioFile 软件编码器零依赖就能做；FLAC 有 AudioToolbox 原生（macOS 10.13+）。真正绕不开三方库的需求可能只有一个（OGG/Vorbis） |
| 2 | **License 是上架生死线，不是细节**：ffmpeg GPL 构建直接堵死 MAS。三方集成前先查 License（GPL/LGPL/MIT），再查体积和形态（CLI 二进制 vs 静态库） |
| 3 | **选型先看运行时语言**：Faster-Whisper 好是好在 Python 场景；原生 Swift App 内置模型推理，第一筛选项是「有没有 C API」（whisper.cpp 胜出，MLX 次之） |
| 4 | **市场事实反推功能决策**：海外 macOS 三条主流链路（备忘→M4A / 播客→MP3 / 音乐→WAV），OGG 需求趋近零——之前「保留 OGG 所以集 ffmpeg」的理由本末倒置了。功能存废先问用户要不要，再谈技术怎么给 |

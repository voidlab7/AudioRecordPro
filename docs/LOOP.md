# LOOP — 开发循环协议（Loop Engineering 落地）

> 2026-09-20 由老板启动，录音 App 为第一个试点。
> 目标：把人从「每步验收」中解放，只保留三个动作——**定义、裁决、签收**。
> 本协议是 Tab 工作的宪法，优先级高于一切临时指令。执行时无须逐条向老板请示，按协议自转。

---

## 一、循环结构

```
L1 目标循环（老板 · 每周）    产品目标 → 拆解 → 需求池（TODOS.md）
L2 交付循环（Tab · 每张单）   实现 → 自验 → 不满足？修 → 满足 → 置 ready-for-review
L3 发现循环（Tab · 持续）     E2E/真机运行 → 发现异常 → 新条目回池
```

- 收敛条件 = **该单的验收标准全部勾满**，不是「没有问题」
- 发现的问题自动成为新条目进池，循环持续，直到池中无 todo

---

## 二、状态机

```text
todo ──→ doing ──→ self-verify ──┬─ 失败（≤3 轮）──→ 修 → 回 self-verify
                                 └─ 机器门禁全绿 ──→ ready-for-review ──→ 立即继续下一张 todo（不等待）
                                                                   ↓ 老板滞后批量签收（次日晨审）
                                                            done   或   打回 → todo（附修正说明）

blocked（轮次耗尽/方向分歧，带证据找老板）
```

**核心修正（2026-09-20 · 自动驾驶化）**：`ready-for-review` 不是终点站，是路标。签收从「同步门禁」改为「滞后质检」——AI 置 `ready-for-review` 后**立即**继续下一张，不停下等老板。老板任何时候（通常是次日早上）批量签收；打回的单带修正说明回 `todo` 重跑。**人不在场不是循环停止的理由。**

状态标记写进 `TODOS.md` 每条目：`[todo]` `[doing]` `[self-verify]` `[ready-for-review]` `[blocked]` `[done]`。

---

## 三、三条规则（不可违反）

1. **单子带标准**：每条需求/Bug 必须带可勾选的验收标准（可机器验证的产物层条件），没有标准不开工；老板未签标准前，Tab 可起草草案但不得开工
2. **做完必自验**：构建 + 测试 + 落盘硬验证全绿，附证据，才允许置 `ready-for-review`；禁止「应该没问题」式口头完成
3. **问题必回池**：自验/运行中发现的新问题，写成新条目回 `TODOS.md`，不许丢在对话里；修 A 时发现 B，B 进池排队，不顺手夹带

---

## 四、刹车（防失控）

| 刹车 | 规则 |
|---|---|
| 轮次上限 | 自验失败 3 轮 → 置 `blocked`，带证据（日志/截图/失败输出）找老板裁决 |
| 单子粒度 | 一张单 ≤ 一次会话能完成（15-30 分钟粒度）；太大的单先拆再开工 |
| **会话预算** | 一次「跑 loop」默认 **2 小时**，到点收束：写状态 → 未完成单留 doing 现场 → 汇报。老板不在场时不自动开新一轮（2026-09-21 教训：通宵 4 小时一半在空转） |
| **同类失败止损** | 同一错误模式连续 **3 次**尝试无进展 → 置 `blocked`，不再自动重试 |
| **系统级故障** | 环境级故障（进程杀不掉/命令反复超时/锁残留）→ **立即停**，等干净环境（如重启系统），AI 不深夜搏斗 |
| 方向分歧 | 两种方案难以取舍 → 停下，描述选项与利弊，让老板拍板，不得自行决定 |
| 测试失败裁决 | 「实现错了还是测试错了」的决定权属于老板 |
| 范围控制 | 只做单子范围内的事；范围外的改进写新条目进池 |

## 六、人工介入点（老板只在三个时点出现）

| 时点 | 动作 | 时机 |
|---|---|---|
| **定义** | 写/改验收标准，或批准 Tab 起草的标准草案 | 开工前（可一次性批量定义 N 张单进池） |
| **裁决** | `blocked` 条目、方向分歧、测试失败定责、P2 批量否决 | 随时，发现即处理 |
| **签收** | `ready-for-review` 条目：只看证据（构建日志摘要/afinfo 字段/日志 grep/截图/回归结论），不盯过程 | **滞后批量**：一次晨审签收一整晚的产出 |

老板不在场时，Tab 不得停下等待——按协议继续跑下一张 todo 单。

---

## 七、证据规范

每条 `ready-for-review` 必须附四样：
1. 构建日志摘要（exit code）
2. 硬验证输出（afinfo 字段 / 日志 grep 关键行 / 截图）
3. 回归结论（哪些旧用例重跑、结果）
4. 验收标准勾选清单（每项标 ✅/❌ 与证据编号）

---

## 八、与既有体系的衔接

- 本协议不取代 Tab 的 AGENT.md 铁律，而是在其上增加循环纪律
- 需求文档仍在 `docs/需求/REQ-*.md`，验收标准以 `TODOS.md` 条目内为准（唯一真相）
- Bug 追踪区条目与 REQ 条目同等适用本协议
- 会话结束但单子未完成 → 状态原样保留在 `TODOS.md`，下次会话读文件继续，老板不重新复述

## 九、运转机制（如何转起来）

### 触发与停止

```text
触发：老板说「跑 loop」/「继续跑 loop」/「自动驾驶」；或 automation 定时触发
执行：读 TODOS.md → 取最高优先级 todo → 交付（实现→自验→修）→ 写状态 → 继续下一张
停止：池中无 todo，或出现 blocked → 停下带证据汇报
```

loop 不是常驻进程，而是**触发即转、转完即停、文件接力**。状态在 `TODOS.md`，会话只是跑道。

### 🚗 自动驾驶模式（Night Loop · 无人值守核心）

> 解决「跑完一张就停」问题的机制本体。人一次性定义 N 张单进池，AI 整夜自转，人次日晨审批量签收。

| 项 | 规则 |
|---|---|
| 触发 | 老板说「自动驾驶」/「夜跑」；或 automation 每晚定时触发（见下） |
| 单张完成后的动作 | 置 `ready-for-review` + 证据落盘 → **立即**取下一张 `todo`，不停下等签收 |
| 停止条件 | ① 池中无 `todo` ② 出现 `blocked` ③ 达到当晚上限（默认 8 张单 / 5 小时，取先到者） |
| 收工动作 | 汇总报告：跑了哪几张、各单状态、`ready-for-review` 清单、`blocked` 清单、证据文件路径 |
| 反阻塞 | 单内遇到歧义 → 写推理继续，**不得停在歧义上等老板**；3 种方案都不行 → 带 TODO 置 `blocked` 继续下一张 |
| 防睡眠 | 自动驾驶前确保 Mac 不睡眠（系统设置或 `caffeinate -i` 挂在驱动命令上） |

**为什么这样设计**（Anthropic 协作悖论 + amux overnight 实践）：人在环但不在循环路径上。老板 1 分钟写 10 张单（定义），AI 8 小时跑完（交付），老板次日 30 分钟批量签收（质检）。签收滞后、批量、看证据——这是「人不在场循环不停」的唯一可行形态。

### 次日晨审协议（滞后签收）

```
① 读报告（2 分钟）   看自动驾驶收工报告，哪些 done / ready-for-review / blocked
② 快审（10 分钟）    每张 ready-for-review 单：看证据四样勾验收标准，快审不过的下拉深审
③ 深审（20 分钟）    可疑单：读 task 摘要 + git diff，重点看「改了范围外吗 / 删测试了吗 / 测试验证的是正确行为吗」
④ 签收或打回         通过 → done；不过 → 打回 todo 附修正说明（回池重跑，不丢）
⑤ 派发（1 分钟/张）   把新 backlog 补验收标准回池，为新一晚备料
```

### Agent 组织（CodeBuddy 机制映射）

| 机制 | 用法 |
|---|---|
| rules（`.codebuddy/rules/loop-protocol.md`） | 宪法每次会话自动加载，行为约束在场 |
| 主对话（Tab 人格） | 编排：读状态 → 派单 → 写回状态 → 汇报 |
| task 子代理 | 每张单的执行单元（上下文隔离，返回摘要） |
| automation | **自动驾驶的定时发令枪**：每晚定时触发「读 TODOS.md，按自动驾驶模式连续跑 todo 单」，maxDurationMinutes 兜底 |
| Team | **暂不用**：异步多 agent 管理成本高，单人串行流水线不需要 |

### Task vs Team 源码实证（2026-09-20，genie 仓库）

- Task 子代理：`agent-craft/src/common/tools/task/`（task-tool.ts / subagent-manager.ts / subagent.ts）——`Subagent extends BaseAgent`，构造时消息**初始为空**（主会话上下文不进入，只注入自身 systemPrompt + prompt），同步 `await` 执行，结果仅回传最后一条文本 + toolCallBrief 摘要（超 12000 字符截断），可改文件，禁用 Task 防递归，maxStep 500
- Team：`agent-cli/src/node/agent-team/`——进程内 AgentTask，文件 mailbox 通信（2s 轮询），持久历史可 respawn，异步跨轮
- 结论：单张单用 Task（轻、隔离、一次性）；Team 仅当需要多 agent 长期并行协作才引入

### 上下文管理

- 每张单优先用 task 子代理执行 → 子代理上下文天然新鲜，主对话不涨
- 主对话上下文涨了 → 直接开新会话，说「继续跑 loop」→ 读 `TODOS.md` 无损续接
- 任务边界写状态：做完一张单先把状态+证据落文件，再开下一张
- **核心认知：上下文清不清不重要，状态不丢在上下文里才重要**

### 会话内自转 vs 会话间断点

- 会话内：Tab 连续跑多张单不等待，直到池空或 blocked
- 会话断：状态无损，新会话续接（这是「做一半就停」问题的根本解——停的不是进度，只是当前跑道）

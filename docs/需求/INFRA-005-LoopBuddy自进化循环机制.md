## 二、① 观察步规格

### 观察什么（MVP 信号源，6 源）

| # | 信号源 | 怎么测 | 有效信号 |
|---|---|---|---|
| 1 | 构建 | `xcodebuild build`（无人值守路径） | 编译失败 / 新增 warning |
| 2 | SDK 单测 | 既有单测入口 | 红测（最强信号） |
| 3 | UI 测试 | `bash scripts/test-ui.sh` | 红测（**当前整条断，LOOP-05**） |

| 6 | 日常观察项 | TODOS.md 各 done 单「留日常观察」备注清单 | 复验失败 / 老板反馈 |

### 什么时候观察 / 入口

- **无常驻守护，不空转**。观察只发生在「一轮 LoopBuddy」内部的第一步。
- 三个触发器（手动 / 定时班次 / 夜跑长班）统一收敛到同一入口协议：**「跑一轮 LoopBuddy」** = 按 §一顺序执行七步。
- MVP 只用手动触发（老板或定时自动化说「跑一轮 LoopBuddy」）；单轮跑稳后，再把定时/夜跑作为外挂挂上。调度变了，协议一字不改。
- 一轮内可处理多张单（执行→自测→交付逐单进行，单间必重读池）。

### 输入输出

- 输入：信号源清单 + 上轮反哺更新过的判据/观察清单 + TODOS.md 当前状态。
- 输出：**观察报告**（每轮必产，哪怕结论是「本轮无事」——报告本身是循环活着的证据，进战报）。

## 三、③ 分诊 A/B 授权边界（初始清单，反哺可修订）

- **A 类（预授权直接开工）**：测试红→修复；构建失败→修复；回归 bug 且验收判据可硬验证；判据文档/知识库与代码的同步。
- **B 类（需老板审核）**：功能新增；交互/视觉改动；L 档调研；判据写不硬的需求；任何动到主窗口生命周期/录音管线的改动。
- 修订规则：A 类边界只能由反哺步依据真实运行证据修订，修订记录留痕；执行侧不得现场扩权。

## 四、刹车与回滚

1. 同一单失败 ≤3 轮即停，状态记 blocked + 原因，继续下一单。
2. 全程 git worktree 隔离，禁动 master；交付在 worktree 分支，验收后 merge。
3. 战报必含：做了什么 / 硬证据 / 回滚命令 / 待验收清单。

## 六、PM 角色 与 上下文分离（2026-10-19 04:09 老板定调）

### 为什么有 PM

老板的三个判断，构成本节的设计依据：

1. **Goal 收敛**：需求交付清楚 = 循环必然到达。验收判据就是不动点——单子带标准（loop-engine 铁律）由此升格为整个循环的收敛条件，判据写得越硬，循环越不需要人。
2. **意图一致性**：PM = 老板产品意图的常驻代理。老板只与 PM 对话（单一接口）；PM 负责让每一张单都长在同一个产品设计上，并复核实现是否偏离意图。
3. **上下文分离**：下发与验收必须是不同上下文，否则无法纠正实现偏差。

### PM 职责

| 职责 | 做什么 | 产物 |
|---|---|---|
| 意图持有 | 吃透老板的产品判断（对标剪映、极简、工业风等既定方向），维护判据文档 | 判据文档（反哺更新的落点） |
| 下发（②③步） | 观察报告 → 需求单（证据+根因假设+验收判据）→ 分诊 A/B | 入池单 |
| 验收复核（⑥→老板之间） | 对判据验硬证据，产出「建议验收 / 打回」意见供老板晨批 | 验收意见 |

### 上下文分离机制（偏差纠正的根）

- **下发上下文**：PM → Tab 的全部信息 = 需求单本身。只含「要什么 / 怎么算对」，不含实现偏好与对话过程。
- **验收上下文**：PM 复核时**只读两样**——需求单判据 + Tab 产出的硬证据。**禁止读 Tab 的实现过程陈述**（防锚定传染与自我合理化）。
- **物理隔离**：同一张单，下发与验收是两个独立会话上下文，不共享对话记忆；唯一共享通道 = 落盘工件（需求单 / 战报 / 证据包）。
- **偏差纠正闭环**：验收发现偏差 → 不直接改代码，回池开 FIX 单（重新下发、新上下文）→ 偏差原因写进反哺。改单不改话。
- **PM 自身漂移的兜底**：PM 写的单也可能偏离老板意图。A 类单判据全是可硬验证的客观标准，漂移面小；B 类单走老板审核关卡；老板交付验收是最终防线。三层兜底，无单层依赖。

### 与既有结构的关系

- 「需求台=Jarvis 兼任」升级为：Jarvis 以 **PM 上下文**运作②③步与验收复核；执行侧 Tab 不变。
- 两道关卡（需求审核 / 交付验收）不变——老板仍然只在两道关卡出现，只是中间多了一层意图一致的保证。

### intent 层执行规格（补 gap：原话落盘）

此前缺口：需求台把老板口述直接编译成方案语言，原话留在会话转录未落盘，验收纠偏无对照锚点。修正：

1. **入口不变**：老板口述/手机消息（触发器：任何会话里的需求表述）。
2. **PM 先写 intent**：按模板落盘 `docs/需求/intent-<主题>.md`，**「发起人原话」节逐条引用不改写**（含口语与不完整句）。
3. **讨论具体化**：老板修订 → 回写 intent 的「待确认问题」逐条关闭。
4. **转 spec**：intent 已审核后，需求台才把它编译成规格文档入池（spec 层）——原话层封存，PM 重写不得覆盖。
5. **验收回溯**：交付验收发现偏差时，对照「发起人原话」判定是实现偏差还是 spec 编译偏差——实现偏差回池 FIX，编译偏差修 spec 重审。

## 八、链路监控规格（2026-10-19 07:40）

### 监控对象：痕迹的新鲜与自洽，不是进程存活

LoopBuddy 无常驻进程，架构上就否掉了「进程活着」这类指标。真正会坏的方式只有四种，按危险度排序：

| # | 维度 | 坏掉的样子 | 判定（脚本实现） |
|---|---|---|---|
| 1 | **心跳** | 触发器挂了 / 没人触发 / 战报没落盘 —— 循环静默停摆，比跑错更危险 | 最新 `docs/LoopBuddy/R*-*.md` 的 mtime：>48h 警告，>96h 失败（挂每日定时后收紧为 26h / 50h） |
| 2 | **自洽** | 战报写「✅ PASS」但证据列空 —— 自我合理化，绿灯是编的 | 解析战报信号源表：PASS 行证据为空即失败；blocked >1 器警告 |
| 3 | **证据新鲜度** | 拿上一轮的旧绿灯冒充本轮；或单测实际有失败却写成通过 | 最新 `test_logs/sdk_test_*.log` 的 `Executed N tests, with M failures`：M>0 失败；日志比战报早 >60min 警告 |
| 4 | **完整性** | 某轮 loop 绕过 worktree 直接改 master | **窗口 = 最近一份战报之后**；窗口内触碰 `AudioRecordApp/` `AudioRecordKit/` `e2e/` 的直达提交即失败 |

辅助两项（同一脚本）：

- **代谢**：`doing`/`self-verify` 滞留 >12h、`rfr` 滞留 >48h → 警告。用以发现「单子卡住没人推」。
  时间取该单在 TODOS.md 最后一次 git 变更（`-G` 匹配），不用文件 mtime（mtime 会被无关编辑刷新）。
- **待执行队列**：已审核 = 0 且待审核 = 0 → 池空警告；已审核 = 0 但有待审核 → 全卡审核关卡警告。

### 实现与调用

- 脚本：`scripts/loopbuddy_health.py`（只读；`--json` 给机器读；每次运行追加一行到 `docs/LoopBuddy/health.jsonl`）
- 退出码：0 健康 / 1 警告 / 2 失败 —— 可直接作为自动化与晨报的分支条件
- **重要**：以 `health.jsonl` 的 verdict 历史看趋势，不要只看单次输出；连续两次 fail 即认定循环不可信

### 监控自身的三条纪律

1. **监控读原始证据，不读结论**：判据来自 git 提交链、测试日志、文件 mtime；战报的自我陈述只作为被校验对象。
2. **监控不得改状态**：体检脚本只读，不推进单子、不重跑测试、不写 TODOS.md。修理由循环体走正常分诊。
3. **告警必须带下一步**：每条失败写明「该看什么」，否则告警会退化成人肉忽略。

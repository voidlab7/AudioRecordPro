# AudioRecordMac 当前能力分析

> 更新时间：2026-05-03
> 本文描述当前代码已实现和仍有限制的能力，避免继续沿用早期“100% 匹配/完全兼容”的过度表述。

## 1. App 层能力

### 已实现

| 能力 | 当前状态 | 说明 |
|---|---|---|
| 全部系统声音录制 | 已实现 | macOS 14.4+ 优先使用 CoreAudio Process Tap；低版本存在 ScreenCaptureKit fallback 路径 |
| 指定进程录制 | 已实现 | UI 支持选择进程；录制器支持设置目标 PID |
| 麦克风录制 | 已实现 | 底层 `MicrophoneRecorder` 可用；当前主 UI 中麦克风更像“附加输入” |
| 麦克风混入系统/进程音频 | 已实现 | `MixedAudioRecorder` 将麦克风与当前系统/进程目标混到单文件 |
| 进程枚举 | 已实现 | 可枚举可录制音频进程并过滤系统/Helper/当前 App |
| 实时反馈 | 已实现 | 波形、电平、轨道、计时器、状态栏 |
| 录音文件列表 | 已实现 | 启动加载本地录音文件，自绘暗色列表 |
| Finder 打开 | 已实现 | 双击或操作后可定位文件 |
| 播放入口 | 部分实现 | 支持播放最近/指定录音的基础路径，仍需更完整的文件行内播放体验 |
| 导出入口 | 部分实现 | UI 有“生成 MP3”，但需校准真实编码格式和文案 |

### 当前主要限制

1. 主 UI 不把“纯麦克风录制”作为第一层主目标，麦克风更偏附加输入。
2. UI 尚未暴露格式选择，默认格式与底层能力之间需要统一。
3. 文件管理不完整：缺删除、重命名、批量操作、导出进度。
4. 权限失败和进程列表为空时的产品化引导不足。
5. 快捷键、菜单栏常驻、定时录制尚未实现。

## 2. SDK 层能力

`AudioRecordKit` 当前已经拆成 Swift Package，目录结构为：

```text
AudioRecordKit/
├── Sources/
│   ├── API/      # public Swift API 和共享类型
│   ├── Core/     # internal 录制器、Process Tap、文件写入
│   ├── CAPI/     # C 头文件与 @_cdecl 导出
│   └── Utils/    # 日志、权限、文件、音频工具
├── Tests/
└── Package.swift
```

### Swift API

当前公开 Swift API 是 MVP 形态：

- `AudioRecordAPI.shared.getUserMedia(constraints:)`
- `AudioRecordAPI.shared.startRecording(stream:)`
- `AudioRecordAPI.shared.stopRecording()`
- `AudioConstraints(includeSystemAudio:)`
- `MediaStream` / `MediaStreamTrack`

能力边界：

| 项目 | 当前状态 |
|---|---|
| 麦克风流 | 支持 |
| 包含系统音频的混音流 | 支持 |
| 指定进程流 | App 控制层支持，Swift MVP API 未完整暴露 |
| 动态轨道 add/remove/clone | 未实现，当前是单轨 MVP |
| deviceId/sampleRate/channelCount/autoGainControl 等 Web 兼容参数 | 未完整实现 |
| 完整 MediaDevices API 兼容 | 不能宣称 |

### C API

C API 头文件声明较完整，包含：

- 生命周期：Create / Destroy / Version
- 控制：Start / Stop / Pause / Resume / State / Duration
- 配置：Format / SampleRate / OutputDirectory
- 回调：Level / State / Complete / Error
- 权限：麦克风、屏幕捕获
- 进程枚举：进程数量、PID、名称、Bundle ID

但实现仍有 MVP 限制：

| 项目 | 当前限制 |
|---|---|
| 系统版本 | C API 创建路径当前偏向 macOS 14.4+，与“macOS 13 基础功能”表述需区分 |
| StartWithProcess | 头文件有接口；实现需继续确认 PID 是否完整传入底层 |
| Pause/Resume | 当前不应作为已完成能力宣传 |
| CAF | 如未真实输出 CAF，不应对外承诺 |
| 屏幕录制权限检查 | 需要补齐真实 preflight/引导能力 |

## 3. 设计模型与实际实现的关系

早期文档中有完整 MediaStream 多轨模型、Web API 完全兼容模型、MVP 极简模型。当前真实状态是：

- App 产品层：多音源录制体验已经比较完整。
- SDK API 层：仍是 MVP，偏单轨和简化约束。
- C API 层：接口形态完整，部分实现仍需补齐。

因此，当前文档口径应统一为：

> App 层录制能力较完整；SDK/C API 是可用骨架 + MVP 实现，不能宣传为完整 Web MediaDevices 兼容。

## 4. 当前最重要的能力缺口

| 优先级 | 缺口 | 原因 |
|---|---|---|
| P0 | 导出格式真实一致 | “生成 MP3”如果不是标准 MP3，会直接影响用户信任 |
| P0 | 权限失败引导 | 系统音频录制高度依赖 macOS 权限，失败时必须可恢复 |
| P0 | 核心路径回归 | 系统音频/指定进程/混麦三条路径必须稳定 |
| P1 | 文件管理闭环 | 录完后的播放、重命名、删除、导出是用户高频动作 |
| P1 | 快捷键 | 桌面工具的效率感依赖快捷操作 |
| P2 | SDK 示例 | 对外集成需要 Swift/C 最小示例和限制说明 |

## 5. 结论

当前工程已经不是纯技术 Demo：它有真实录制能力、清晰 UI 和基本文件闭环。但它也还不是完整发布级产品。下一阶段应聚焦“可信闭环”：录得稳、权限能修、文件能处理、文案不误导。

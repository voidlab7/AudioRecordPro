## 1. 测试能力评估

### 自动化测试（SPM 单元测试）

项目已有 `AudioRecordKit/Tests/` 下 6 个测试文件，可通过 `swift test` 运行。

**能覆盖的**：
- `AudioFormat` 枚举属性（采样率、位深、声道数）
- `AudioDataConversionError` 错误描述
- `AudioFileInfo` 格式化输出
- Process Tap 常量定义

**不能覆盖的**（硬件依赖，必须人工测试）：
- Process Tap 创建和音频捕获
- 聚合设备绑定和 IO 回调
- 实际音频数据写入和文件完整性
- 热插拔设备切换
- 长时间录制稳定性
- 启动延迟测量

### 结论

> REQ-1.0-01 的 5 项验收标准**全部需要人工测试**。自动化测试只能验证辅助逻辑。

## 2. 人工测试用例

### TC-01: 基本录制 — 系统音频捕获与回放

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #1 基本录制 |
| **优先级** | P0 |
| **前置条件** | App 已编译启动；系统扬声器设置为 48kHz |

**测试步骤**：

1. 打开 App，在侧边栏选择 **"全部系统声音"**
2. 打开浏览器，播放一段 **YouTube 视频**（有人声+背景音乐的）
3. 点击 App 的 **录制按钮**（红色圆形）
4. 等待 **30 秒**，观察：
   - [ ] 录制按钮变为红色方形（RECORDING 状态）
   - [ ] 时间显示正常递增
   - [ ] 电平表有波动（说明在接收音频数据）
5. 点击 **停止按钮**
6. 在文件列表中找到刚录制的文件，点击 **播放**
7. 验证：
   - [ ] 回放声音清晰，无杂音、无爆音
   - [ ] 回放内容与 YouTube 视频声音一致
   - [ ] 录制期间 YouTube 视频声音正常（用户无感）

**预期结果**：录制成功，回放清晰，录制期间不影响正常听音。

### TC-02: 音频格式验证 — 采样率与位深

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #1 基本录制（技术规格） |
| **优先级** | P0 |
| **前置条件** | TC-01 录制的文件存在 |

**测试步骤**：

1. 找到 TC-01 录制的 WAV 文件路径（在 `~/Documents/AudioRecordings/` 下）
2. 在终端执行：
   ```bash
   afinfo ~/Documents/AudioRecordings/<文件名>.wav
   ```
3. 验证输出中：
   - [ ] `Sample Rate: 48000.0`（匹配系统扬声器设置）
   - [ ] `Bit Depth: 16`（16-bit PCM）
   - [ ] `Num Channels: 2`（立体声）
   - [ ] `Data format: 2 ch, 48000 Hz, 'lpcm'`（线性 PCM）
4. 用第三方播放器（如 VLC / QuickTime）打开文件，确认可正常播放

**预期结果**：文件格式为 48kHz / 16-bit PCM / 立体声 WAV。

### TC-03: 不同采样率设备验证

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #1 基本录制（DR-01 架构决策验证） |
| **优先级** | P0 |
| **前置条件** | 可以修改系统音频输出设备采样率 |

**测试步骤**：

1. 打开 **系统设置 → 声音 → 输出**，将扬声器采样率改为 **44100 Hz**
2. 重新启动 App
3. 选择"全部系统声音"，录制 **10 秒** 音频
4. 停止录制，用 `afinfo` 检查文件：
   - [ ] `Sample Rate: 44100.0`（跟随设备，不是硬编码 48000）
5. **播放录制的文件**：
   - [ ] 声音正常，**不变调**（不变快也不变慢）
6. 将扬声器采样率改回 **48000 Hz**，重复步骤 2-5
   - [ ] `Sample Rate: 48000.0`
   - [ ] 声音正常，不变调

**预期结果**：文件采样率跟随设备实际采样率，回放不变调。

> ⚠️ **这是矩纠正的关键测试**：如果硬编码 48kHz，在 44.1kHz 设备上录制会变调。

### TC-04: 启动延迟

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #2 启动延迟 < 100ms |
| **优先级** | P1 |
| **前置条件** | App 已启动 |

**测试步骤**：

1. 选择"全部系统声音"
2. 播放一段有节奏的音频（如节拍器 App 或有明显节拍的音乐）
3. 在一个明确的节拍点**点击录制按钮**
4. 录制 10 秒后停止
5. 播放录制的文件，检查：
   - [ ] 录制开头是否包含了点击时刻的节拍声
   - [ ] 没有明显的"吞头"现象（开头不缺失）
6. 观察 App 日志（如有），检查初始化耗时：
   - [ ] 从点击到第一个音频回调 < 100ms

**预期结果**：录制几乎立即开始，无明显延迟。

> 💡 精确测量需要 Instruments 工具，人工测试主要验证"感知上无延迟"。

### TC-05: 长时间录制稳定性

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #3 连续录制 4 小时无崩溃 |
| **优先级** | P0 |
| **前置条件** | 磁盘空间 > 5GB |

**测试步骤**：

1. 选择"全部系统声音"
2. 播放一个 **长时间音频源**（如 YouTube 直播、长播客）
3. 点击录制，**持续录制至少 30 分钟**（完整验收需 4 小时）
4. 录制期间每 10 分钟检查一次：
   - [ ] App 未崩溃
   - [ ] 时间显示正常递增
   - [ ] 电平表仍有波动
   - [ ] 系统内存使用无异常增长（活动监视器检查）
5. 停止录制
6. 验证：
   - [ ] 文件大小合理（48kHz/16-bit/立体声 ≈ 11MB/分钟）
   - [ ] 回放完整，尾部无损坏
   - [ ] `afinfo` 显示的时长与实际录制时长一致

**预期结果**：长时间录制无崩溃，文件完整。

---

### TC-06: 热插拔设备

| 字段 | 内容 |
|------|------|
| **对应验收标准** | #4 热插拔 |
| **优先级** | P1 |
| **前置条件** | 有外接耳机（有线或蓝牙） |

**测试步骤**：

1. 使用**内置扬声器**，选择"全部系统声音"，开始录制
2. 录制 10 秒后，**插入有线耳机**（或连接蓝牙耳机）
3. 观察：
   - [ ] App 未崩溃
   - [ ] 录制继续（时间仍在递增）
   - [ ] 状态栏可能显示"音频设备已切换"
4. 继续录制 10 秒
5. **拔出耳机**（或断开蓝牙）
6. 观察：
   - [ ] App 未崩溃
   - [ ] 录制继续
7. 再录制 10 秒后停止
8. 播放录制的文件：
   - [ ] 整段录音都有声音（设备切换前后都有）
   - [ ] 切换点可能有短暂静音，但不应有爆音或崩溃

**预期结果**：录制中插拔耳机不崩溃，音频正常切换。

### TC-07: 进程级录制（附加验证）

| 字段 | 内容 |
|------|------|
| **对应验收标准** | 附加（为 REQ-1.0-02 做准备） |
| **优先级** | P2 |
| **前置条件** | 有正在播放音频的应用（如 QQ 音乐） |

**测试步骤**：

1. 打开 QQ 音乐并播放一首歌
2. 在 App 侧边栏的进程列表中找到 **QQMusic**
3. 选中 QQMusic，点击录制
4. 录制 15 秒后停止
5. 播放录制的文件：
   - [ ] 只有 QQ 音乐的声音
   - [ ] 没有其他应用的声音混入

**预期结果**：仅录制指定进程的音频。
